# Sona 项目工程交接文档

> 交接日期：2026-08-15  
> 交接状态：本轮仅整理交接，不改代码、不改数据库。  
> 给下一位工程师的话：这个项目已经不是“概念 Demo”，而是一套可播放本地音乐、支持歌单与初步云同步的 Windows + Android 产品原型。接手后先稳定数据结构与同步，不要一上来同时重构 UI、云端和播放器底层。

## 一、项目定位

Sona 是一款离线优先的个人音乐播放器，主要平台为 Windows 和 Android，目标体验接近离线版网易云音乐 / Spotify：

- 导入和播放 MP3、MP4/MV；
- 本地曲库、收藏、最近播放、歌单、听歌排行；
- MP3 与 MV 配对，也允许只有 MP3 或只有 MV；
- 黑胶唱片播放页与 MV 播放页；
- 自定义背景、头像、歌单封面及裁切；
- 多套主题，视觉方向为“LocalSend 旗舰极简 + 液态玻璃 + 年轻化多巴胺配色”；
- 使用云账号在多台设备之间同步个人资料和音乐数据。

当前优先级：Windows + Android。Mac 可作为后续兼容项，iOS 暂不做。

## 二、技术结构

- 客户端：Flutter，一套代码适配 Windows 和 Android。
- 本地数据：SQLite。离线时仍应完整可用，本地原文件不得被应用擅自覆盖。
- 云端：Supabase。
  - 项目名：`sona-cloud`
  - Project Ref：`mtikxsgwhzommksflewe`
  - URL：`https://mtikxsgwhzommksflewe.supabase.co`
  - 使用 Auth、PostgreSQL、Storage。
- 视觉参考文档：早期本地设计参考（未纳入仓库；当前实现以 `docs/design/` 为准）
- 当前真实版本号必须从项目的 `pubspec.yaml` 读取；不要相信旧截图，旧手机截图曾显示过 `0.4.1`。
- Supabase 客户端只可使用 publishable/anon key，绝不能把 `service_role` key 放入客户端、日志或交接文档。

## 四、当前最重要的未完成问题

### 1. 云同步还不是真正的双向同步

当前表现偏向“把本机内容上传”，恢复内容和提示语也不完整。目标必须是：

- 本地有、云端没有：上传；
- 云端有、本地没有：下载；
- 两边都有：按稳定 ID、内容哈希和更新时间判断，不重复创建；
- 同步范围包括歌曲、媒体文件、歌单、歌单与歌曲关系、收藏、播放记录、排行、歌单封面、头像、昵称和必要设置；
- 同步完成后明确展示上传和下载结果，不能只说“已同步”。

### 2. 歌单封面没有随歌单恢复

歌单本身可能已经从云端创建到另一设备，但封面未下载或未重新绑定。本地歌单、云端歌单、Storage 对象三者缺少完整的一致性链路。

### 3. Supabase 数据库存在结构漂移

历史上出现过：

- `profiles already exists`；
- `profiles.username` 不存在导致 `PGRST204`；
- `Email signups are disabled`；
- Auth 总开关与 Email provider 开关配置不一致。

因此接手后不能继续盲目加 SQL。先对照客户端查询字段、数据库真实表结构、RLS policy 和 Storage policy，做一次只读审计，再编写可重复执行的迁移。

### 4. 账号名与昵称容易混淆

- 账号名：注册时确定，用于登录，应该长期稳定且始终可见，例如 `yan`。
- 昵称：对外显示，可修改并同步，例如 `Sona Demo`。
- “修改名称”统一改为“修改昵称”。
- 登录状态建议展示：昵称为主、`@账号名` 为辅。
- 目前为了先实现用户名登录，Auth 内部可能使用 `username@accounts.sona.local` 形式的合成邮箱。它是实现细节，不应直接暴露给普通用户。

### 5. Windows 左下角账户区未完全联动

- 未登录：显示“本地模式 / 登录云账号”。
- 已登录：显示头像、昵称和 `@账号名`，不再显示“本地模式”。
- 点击账户区：跳转到“设置 → 账号与云同步”。
- 手机端和电脑端必须读取同一份账户状态模型。

### 6. 后台播放和系统媒体通知尚未成为完整原生体验

Android 的 MediaSession、前台播放服务、锁屏/通知栏控制、耳机按键和后台保活仍属于后续独立阶段。不要和云同步同时开发。

### 7. AI 歌曲/歌手/封面识别尚未完成

这是后续增强功能。应在云同步稳定后再做，避免同时改变元数据来源与同步模型。

## 五、双向同步的统一契约

下一位工程师必须先把下面规则写进代码和数据库设计，再写界面。

### 唯一标识与去重

- 用户：Supabase `auth.users.id`。
- 歌曲媒体：优先使用 `content_hash` 去重，同一文件在多设备只保存一份云对象。
- 歌曲记录：使用稳定 UUID，不能用本机文件路径当跨设备 ID。
- 歌单：稳定 UUID；同一 UUID 更新，不因名称相同就随意合并。
- 歌单歌曲关系：`playlist_id + track_id` 唯一。
- 收藏：`user_id + track_id` 唯一。
- 播放事件：追加写入，并以 `client_event_id` 做幂等，防止同一设备重传后排行翻倍。
- 头像、歌单封面：保存 Storage 路径/版本或内容哈希；资料更新后其他设备可判断是否需要下载。

### 冲突规则

- 元数据和昵称：先采用 `updated_at` 较新的版本；每次覆盖必须记录更新时间。
- 媒体文件：按内容哈希判断，永不直接覆盖用户本地原文件。
- 播放事件：只追加、不覆盖；相同 `client_event_id` 只计一次。
- 删除：后续应使用 `deleted_at`/tombstone 传播删除，不能仅在本机物理删除后假装完成同步。
- 第一期如果尚未实现云端删除传播，界面必须明确说明，不能静默误删另一设备内容。

### 同步顺序

1. 校验登录会话与数据库版本。
2. 拉取云端清单与时间戳，不先下载大文件。
3. 比较本地和云端差异，生成同步计划。
4. 上传本地独有资料和文件。
5. 下载云端独有资料和文件。
6. 同步歌单关系、收藏、播放事件和资料设置。
7. 本地事务提交；失败时保留可重试状态。
8. 展示结果并写入最近一次同步记录。

### 用户可读的结果文案

示例：

> 同步完成：上传 3 首歌曲，下载 2 首歌曲；新增 1 个歌单，更新 2 个歌单封面；收藏与播放记录已同步。4 个项目无变化。

失败时只显示用户能处理的信息，详细异常写日志，不要把整段 `PostgrestException` 红字直接扔到界面。

### 阶段 3：歌单双向同步与封面（建议拆成 3 次对话）

3A：歌单元数据双向同步。  
3B：`playlist_tracks` 关系双向恢复，保证排序。  
3C：歌单封面上传、下载、缓存刷新与默认封面回退。

验收：A 新建含封面的歌单，B 同步后名称、描述、曲目、顺序和封面一致；再次同步不重复。

### 阶段 4：收藏、播放记录与排行（建议拆成 2 次对话）

4A：收藏双向合并；播放事件用 `client_event_id` 幂等上传。  
4B：近 7 天、本月、总排行统一从正确数据源计算，并修复旧数据兼容。

验收：同一播放事件重复同步不增加次数；跨设备排行一致；播放满 70% 才计一次的规则有测试。

### 阶段 5：账号资料和 Windows 账户区（建议拆成 2 次对话）

5A：明确账号名/昵称模型，头像和昵称双向同步。  
5B：Windows 左下角账户区与设置联动，补齐登录/退出后的实时刷新。

验收：两台设备登录同一账号显示同一头像和昵称；账号名不可被“修改昵称”改变。

### 阶段 6：Android 原生播放体验（独立项目阶段）

- MediaSession；
- 前台播放服务；
- 通知栏和锁屏播放控制；
- 后台播放、耳机按键、系统媒体音量；
- Android 13+ 通知权限和生命周期测试。

验收：熄屏、切后台后继续播放；通知栏可暂停、上一首、下一首；系统回收后状态合理恢复。

### 阶段 7：AI 元数据识别（同步稳定后再做）

- 先解析文件标签与文件名；
- 再设计可选的在线识别，不允许无提示改错歌曲；
- 候选结果必须让用户确认；
- 识别后的歌手、歌名、封面再进入正常同步。

## 九、产品经理视角的客观评价

Sona 的 MVP 已经成立：核心播放价值明确，Windows 和 Android 均可运行，本地曲库、歌单、收藏、MV、主题与初步账号体系形成了完整产品轮廓。它已经超过普通界面 Demo，具备继续打磨为个人长期使用软件的价值。

当前主要风险不是“功能太少”，而是云端数据模型、幂等同步、跨设备一致性和 Android 原生后台播放还没有达到可靠软件的标准。下一阶段应减少新增功能，把双向同步和数据安全做扎实。完成歌曲、歌单、封面、收藏和播放记录的稳定双向同步后，Sona 才能从“不错的 MVP”进入“可放心长期使用的 Beta”。

### 差异与风险清单

| 项目 | 结论 | 证据 / 影响 |
|---|---|---|
| 真实 Supabase schema、RLS、Storage policy | **未验证** | 本地只有三份迁移，当前没有可用于只读核验线上项目 schema/policy 的管理访问方式；不能把迁移脚本当作线上事实。 |
| 初始迁移的可重复执行性 | **不满足** | `202608150001_sona_cloud_foundation.sql` 多数 `create table/policy/index/trigger` 未使用幂等保护；重复执行会触发 `already exists` 类错误。 |
| 歌单跨设备标识 | **不满足统一契约** | 本地歌单使用整数 ID；云同步按歌单 `name` 匹配，而非稳定 UUID。重名歌单会被错误合并。 |
| 歌单曲目同步 | **非增量且有覆盖风险** | 上传时会先删除该云歌单的全部 `cloud_playlist_tracks`，再重新插入；不适合并发修改，也未同步封面。 |
| 歌曲同步 | **已有初步双向能力** | 按 `content_hash` 上传/下载，使用 `space_id + content_hash` upsert；大于 50 MiB 的文件会跳过上传。尚未完成端到端空设备验证。 |
| 播放事件 | **已有幂等基础** | 客户端以 `user_id, client_event_id` upsert，迁移包含对应唯一索引；实际线上索引存在与否未验证。 |
| 账号模型 | **基本符合方向，仍待线上校验** | 登录使用内部合成邮箱，界面展示账号名；`profiles` 迁移含 `username`，客户端读写资料主要依赖 Auth metadata + `profiles`。 |

- **液态玻璃不是覆盖率越高越好，而是信息层级工具。** 适合强化承载主要内容、需要与摄影背景拉开层次的独立卡片，例如播放器主控制面板、设置主体、搜索与筛选区域、重要快捷入口和缺失媒体状态框。常驻操作层（底部导航、迷你播放器）与高频重复列表若同时使用重模糊、亮边和高透明白层，会连成大片灰白表面，遮挡主题背景、削弱主次、增加视觉厚重感，并可能提高滚动重绘成本。此类区域应使用更克制的浅色表面、弱描边和低强度主题染色。以后引入任何新材质前，应先判断它承担的是“主要内容”“常驻操作”还是“重复列表”，再决定玻璃强度，而不是全局统一套用。
- **单张成品截图不等于可直接实现的交互设计源文件。** 截图只保留最终像素，原始图层、模糊蒙版、材质参数、矢量图标、布局约束、交互热区、播放/暂停状态、拖动状态、不同屏幕比例和动态过渡都已经丢失。若截图中还烘焙了唱片、按钮、进度条和玻璃折射，再在 Flutter 上覆盖真实控件，必然容易出现双层元素、材质不一致、坐标漂移、分辨率不足和状态无法同步。此前青柠参考播放器实验失败的根本原因是输入资产与目标任务不匹配，并非播放逻辑本身过难。
- **Sona 更可靠的高完成度路线是从结构到细节逐层构建。** 先确定信息架构、响应式布局、真实交互组件和状态机，再建立颜色、圆角、间距、模糊、描边、阴影等设计令牌；随后逐个区域对照参考图调整比例和材质，最后通过真机截图小步验收。这样每一层都可编辑、可测试、可复用，也能在已有稳定框架上持续小修小改。参考截图仍然很有价值，但应主要用于提取构图、比例、颜色和质感，而不应把整张带 UI 的扁平图片直接当作实时界面。
- **若必须高精度复刻成品图，应先补齐中间设计资产。** 最佳输入是 Figma/Photoshop/Affinity 的分层文件、独立背景、玻璃蒙版、矢量图标和各交互状态；若只有截图，则先做尺寸测量、区域拆分和静态原型，确认一个区域后再接入真实逻辑。避免一次性同时复刻背景、播放器结构、材质、动画和全部交互，否则问题来源无法隔离，返工成本会迅速放大。

- 深色主题不能只靠压暗：必须保留可识别的纹理、中间调和轮廓。海洋、皮革、岩浆、金属等主题首先要让材质和主体可见，再处理氛围。
- 唱臂可以跟随主题色，但必须取背景中较和谐、偏柔和的颜色，避免高饱和荧光感；默认中性主题继续使用白色或中性色。
- 内外壁纸允许不同，但必须是有意设计且属于同一视觉世界；若用户要求原图一致，应直接复用同一资产或做确定性局部编辑，不能用生成式“近似”替代。
- 参考图只提取色彩、材质、构图和气质；不能把状态栏、文字、按钮、卡片或其他现成 UI 烘焙进背景图。
- 壁纸必须放入真实手机 UI 叠层中检查。单独看图好看不代表文字、卡片、唱片和系统状态栏叠加后仍然成立。
- “查看全部”等高频入口首先保证可发现性和对比度，不机械地全部换成主题色；可根据背景选择高对比色、互补色或提示色。
- 已确认的手机端布局、信息层级和交互逻辑是后续工作的稳定接口。新主题和桌面端开发不应顺手改动这些已验收结构。
